## 1. Анализ характеристик качества по стандарту ISO/IEC 25010

Проектирование архитектуры, процессов ветвления и конфигурации АИС «Кафедральный кампус» опирается на 8 ключевых характеристик качества:

1. **Функциональная пригодность (Functional Suitability):** Система полностью покрывает потребности вуза за счет интеграции модулей расписания, электронного журнала и личного кабинета. Автоматические уведомления (`feature/schedule-notifier`) обеспечивают полноту и актуальность доставки информации пользователям.
2. **Надежность (Reliability):** Отказоустойчивость при сбоях обеспечивается изоляцией кода в Git Flow (в `main` попадает только протестированный продукт) и логическим разделением шлюза синхронизации оценок (`feature/grades-sync`), что минимизирует риск падения всей системы при недоступности внешних баз данных.
3. **Производительность и эффективность (Performance Efficiency):** Шлюз синхронизации оценок оптимизируется по времени отклика и пропускной способности. На уровне конфигурации (`appsettings.json`) предусматривается настройка пула подключений (Connection Pooling) к PostgreSQL для эффективного потребления памяти под высокой нагрузкой в сессионный период.
4. **Удобство использования / UX (Usability):** Пространство личного кабинета студента и интерфейса преподавателя проектируется интуитивно понятной. Для разработчиков и внешних интеграторов удобство использования API обеспечивается интерактивной документацией **Swagger UI**, позволяющей быстро тестировать эндпоинты расписания и оценок.
5. **Безопасность (Security):** Реализована строгая защита персональных данных студентов и оценок от несанкционированного доступа. Безопасность развертывания гарантируется полным исключением явных паролей и API-ключей из репозитория (принцип беспарольного доступа локально).
6. **Сопровождаемость (Maintainability):** Команда может легко модифицировать проект и исправлять баги, так как код разбит на изолированные модули, задокументирован в Swagger UI, а фичи разрабатываются в независимых ветках, что упрощает проведение Code Review.
7. **Совместимость (Compatibility):** Обеспечивается обратная совместимость клиентской части со старыми версиями API шлюза. Изменения в схемах данных (например, при передаче оценок) версионируются в контроллерах и наглядно отображаются в Swagger UI.
8. **Переносимость (Portability):** Следование концепции *Configuration as Code* позволяет легко разворачивать АИС в различных окружениях (Local, Staging, Production) без изменения самого программного кода — достаточно подменить файл конфигурации или переменные среды.

## 2. Схема ветвления (Git Flow)

Для параллельной и безопасной работы команды инженеров принята методология **Git Flow**.

### Роли веток:
* `main` — стабильный релизный код в продакшене.
* `develop` — основная ветка для интеграции готовых модулей.
* `feature/schedule-notifier` — ветка разработки модуля уведомлений.
* `feature/grades-sync` — ветка разработки шлюза синхронизации оценок.

### Визуализация жизненного цикла (Структура веток):
```text
GitFlow-Lifecycle/
|
├── main (Продакшн-версия системы)
|   └── [Релиз] <--------------------------------------┐

|                                                      | (Слияние при релизе)
├── develop (Основная ветка интеграции кода)           |

|   ├── [PR] от feature/schedule-notifier -----------> |
|   ├── [PR] от feature/grades-sync ---------------> |
|   └── [Слияние] стабильного кода в main -------------┘
|
├── feature/ (Временные ветки разработки)
|   ├── schedule-notifier (Модуль уведомлений)
|   └── grades-sync (Шлюз синхронизации оценок)
|
└── hotfix/ (Экстренные исправления багов на проде)
    └── [Фикс] -> Слияние напрямую в main и develop
```

### Командный алгоритм работы:
1. Создание ветки от актуального `develop`:
   ```bash
   git checkout develop
   git pull origin develop
   git checkout -b feature/schedule-notifier
   ```
2. Разработка фичи, фиксация изменений и отправка в репозиторий:
   ```bash
   git add .
   git commit -m "feat: добавлен функционал рассылки изменений расписания"
   git push origin feature/schedule-notifier
   ```
3. Интеграция в `develop` происходит через **Pull Request (PR)** только после успешного ревью и прохождения автоматических тестов.

## 3. Конфигурационная модель (Configuration as Code)

Принцип **Configuration as Code (CaC)** декларирует, что вся инфраструктурная структура описывается в виде конфигурационных файлов, которые хранятся и версионируются вместе с кодом, но **не содержат в себе реальные секреты**.

### Шаблон конфигурационного файла `appsettings.json`
```json
{
  "Logging": {
    "LogLevel": {
      "Default": "Information",
      "Microsoft.AspNetCore": "Warning"
    }
  },
  "AllowedHosts": "*",
  "Swagger": {
    "Enabled": true,
    "RoutePrefix": "swagger"
  },
  "ConnectionStrings": {
    "PostgresDb": "Host=pg-campus.edu.local;Port=5432;Database=campus_db;Username=Nekit;Password=PASSWORD;Maximum Pool Size=100;"
  },
  "SmtpSettings": {
    "Server": "smtp.campus.edu",
    "Port": 587,
    "SenderEmail": "notifier-bot@campus.edu",
    "ApiKey": "API_KEY"
  }
}
```

### Безопасность секретов:
* **Критически уязвимые параметры:** Поля `Password` (доступ к БД PostgreSQL) и `ApiKey` (доступ к почтовому шлюзу для рассылки уведомлений) **запрещено** публиковать в открытом виде.
* **Механизм защиты:** В Git коммитится только данный шаблон с плейсхолдерами. Разработчики локально используют **.NET User Secrets**, а на продакшн-сервере параметры подставляются через переменные окружения контейнеров.

## 4. Решение интеграционного кейса / конфликтных ситуаций

### Кейс 1: Разрешение конфликтов слияния (Merge Conflict)
При одновременном изменении инженерами одного файла (например, при обновлении схемы Swagger или общих моделей данных) возникает конфликт.
1. Загрузить актуальный `develop` и инициировать слияние в свою ветку:
   ```bash
   git checkout feature/schedule-notifier
   git fetch origin
   git merge origin/develop
   ```
2. Открыть файлы со статусом конфликта в IDE. Найти разделители `<<<<<<<`, `=======`, `>>>>>>>`.
3. Совместно со вторым разработчиком принять архитектурное решение, объединить код, сохранить изменения.
4. Зафиксировать разрешение конфликта:
   ```bash
   git add .
   git commit -m "fix: разрешен конфликт интеграции с develop"
   git push origin feature/schedule-notifier
   ```

### Кейс 2: Обнаружение незащищенных секретов в репозитории
Если приватный пароль от базы данных PostgreSQL или токен SMTP был случайно закоммичен:
1. **Ротация доступов:** Немедленно сменить скомпрометированный пароль на реальном сервере БД и отозвать API-ключ.
2. **Очистка истории репозитория:** Использовать специализированную утилиту `git-filter-repo` (обычный новый коммит поверх не сотрет данные из истории Git):
   ```bash
   git-filter-repo --invert-paths --path appsettings.json
   ```
3. **Форсированное обновление:** Отправить чистую историю в удаленный репозиторий с флагом `git push origin --force`.
4. **Защита в CI/CD:** Внедрить инструмент Gitleaks/Trufflehog для автоматического сканирования коммитов на наличие паттернов паролей перед пушем.

## 5. Правила для файла .gitignore

Для предотвращения засорения репозитория временными и локальными файлами среды разработки Visual Studio и платформы .NET, в корне проекта создается файл `.gitignore` со следующими правилами:

```gitignore
## Результаты компиляции, сборки и кэш .NET
bin/
obj/

## Локальные папки конфигурации и кэша Visual Studio
.vs/
*.user
*.userosscache
*.sln.docstates

## Локальные файлы конфигурации, содержащие секреты разработчиков
appsettings.Development.json
secrets.json

## Временные файлы операционных систем
Thumbs.db
.DS_Store
```

## 6. Выводы

Использование систем контроля версий (**Git**) вкупе со стратегией **Git Flow** позволяет команде из 3 инженеров бесконфликтно и прозрачно вести параллельную разработку критических модулей АИС «Кафедральный кампус». 

Соблюдение стандартов **Configuration as Code**, разграничение доступов, изоляция секретов через `.gitignore` и документирование контрактов через **Swagger UI** закладывают прочный фундамент под архитектурные требования **ISO/IEC 25010**. Данный комплекс мер гарантирует высокую **надежность**, **безопасность**, **сопровождаемость** и **переносимость** информационной системы, минимизируя риски сбоев учебного процесса вуза.
